# Changes

Changes (`components/changes.tsx`) is where a person reads what the agents changed in a checkout, answers it, and takes a change back. It is a dock tab of the project (`changes:<machine>/<folder>`, `changesKey` in `lib/dock.ts`), opened by `Review changes` (`mod+shift+g`, `reviewChanges` in `lib/changes.ts`), which means the checkout of the focused tab, else of the project in view. While a chat is in front and the window is not narrow it opens **beside** the chat (a split, `design/tabs.md`) and a second press shows the same tab: the chat and its waiting question stay in view. On a Changes tab, `Open beside` puts the folder's chat next to it.

Everything below is today's behaviour and the rules for reading git do not change.

## Reading it as a review (2026-11-08)

Owner complaint: the tab opened beside a chat gave the diff 215 pt of a 640 pt pane, wrapped its code one character a line and cut its buttons, with 877 files listed of which 874 were a run's output. Decided and built:

- **Scope.** Opened from a chat's `Edited 7 files` the tab carries the paths the agent's edit calls touched (`TurnEffects.edited.paths`, `openChanges(..., { edited })`, `lib/changes-scope.ts`) and opens on those files that git reports a change for (absolute or relative paths, a moved file by either name; the rest dropped). A segmented control in the header, `This session · 7` and `Everything · 877`, switches; the chips carry the file counts and the line after them (`+475 −28`, `2 of 7 reviewed`) is the chosen scope's. From the sidebar, the palette or `Review changes` it opens on everything with no control; an open tab keeps its choice. A session none of whose files git still reports opens on everything. Not built: the chat header's `Changes` chip still opens on everything, because the header has no list of the turns' edits.
- **Output stays out of the way.** More than 12 files git does not know (`NEW_FOLD_ABOVE`) go to one closed section `Not in git · 874` that holds their folders (closed too, with counts); files the session wrote stay in the ordinary groups; a filter opens what matches. A new file that is big or looks like output (`isBulky`: 256 KB, 4,000 lines, or 32 KB of json, csv, log, parquet and the like) is not read at all: `New file · 1.9 MB · 40,000 lines` and `Open anyway`. Rust already cuts a diff at 6,000 lines or 2 MB (`Show all` lifts it) and counts lines of an unknown file up to 64 MB; nothing was missing there.
- **Layout from the pane's own width** (`layoutFor`, `lib/changes-layout.ts`; the root's `onLayout`, never `narrow()`): from 900 pt the files stand in a 288 pt column; below, one bar above the diff holds `‹ 3 of 7 ›` (`j` and `k`), a `Files` button (`f`) that opens the list in a sheet over the pane with the filter focused (it closes when a file is chosen, on Escape or on a press outside), `Mark reviewed`, the note button and the menu, and under them the file named whole (name, then folder, state and numbers). Under 720 pt the header takes two lines (identity and reload, then the scope, counts and progress) and a lean header says `main` for `main · 4 ahead`; no control is cut at 480 pt.
- **Code never wraps below forty columns** (`mayWrap`, `maySplit`): a diff narrower than that scrolls sideways (the renderer's own scroll and edge fades) and side by side needs forty in each half. Unverified and not done: the line-number gutter scrolls with the code, a fixed gutter is a change in `native/app/src/highlight/view`.
- **Review flow.** `Mark reviewed` (`x`) marks the file and moves to the next unreviewed one below it in the list, never back; at the end it says `All reviewed` once and the header's progress reads `All reviewed`. A reviewed row is dimmed with its check. The list head has a `Biggest change first` toggle (per tab, not remembered). Stepping files with `j`, `k` or the pager walks every file of the scope in list order and opens the folded group of the file it lands on.

## What it shows

- **Header, one line** (`Changes`): `payments · main · by 2 agents` on the left, `8 files +38 −8 0 of 8 reviewed` on the right (tabular figures, `+` green, `−` red, the reviewed count at foreground weight once it is above 0). The project and the branch are never dropped; the agent, then the machine (only for another computer, `machineName`) are whole or left out by their measured widths (`identityFit`), a project or branch that is really too long fades (`Clipped` with `fade`). A part git or the board does not know is left out, not a placeholder; before git answers the line is the project and a quiet `Reading changes…`. The agents are those working in the checkout now (`agentPart`: the one agent's name, else `2 agents`, the tip lists them): it is who can be sent notes, not proof of who wrote the change.
- **Left, the files** (`ChangesList`): a quiet 28 pt filter (`SearchField` `dense`) and the changed files grouped **by folder** (`groupFiles`, `lib/changes-tree.ts`): `Merge conflicts` first (they need a decision, warning tone), then `Top level` (files at the repository root), then each folder that holds a changed file, by path. A heading (28 pt) names the folder's whole path once (`native/app/src`), folds its files and keeps its count; a chain of folders with no changed file of its own gets no heading, so nothing is repeated and two `engine.rs` in two folders are told apart by their heading, not by a cut path beside the name. Owner complaint 2026-11-08: the name was cut by a folder text and the numbers sharing one narrow line, and status groups made 18 identical `M` rows. A row is 32 pt (`ROW.agentCompact`), indented under its heading: a 12 pt mark column that holds a letter only for what is not an ordinary edit (`KIND_MARK`: A, D, R, U, `!` in the warning tone; a plain modified file has none), the file name whole in all the room that is left (only a name longer than the row ends in an ellipsis, never a fade, and the tip has the path), `+12` green and `−3` red in a reserved right-aligned column (`binary` or a size in grey when git counted no lines), and a check once reviewed. Files inside a folder go by name. The selected row is one fill (`bg-accent`), no edge; its accessible name is `src/auth.ts, modified, +12 −3, reviewed` (`fileLabel`), a heading's is `src, 5 files`. The list is a virtual `List`: 500 files draw a screenful.
- **Right, the change** (`ChangesDiff`): the selected file as a `DiffBlock` (highlighted, words that changed marked, unchanged stretches folded, unified or split by `diffSplit`; the block does not repeat the path, which is in the header above it, and its own header always shows `Previous change`, `Next change` and `Change 2 of 5`), a row of what can be done (`Mark reviewed` and `Add note` are small outline buttons with their keys, the file's menu a 28 pt icon button), the notes written on the file and the one being written. A binary file, a file with merge conflicts, a nested repository and a file whose only change is its mode each say so instead of drawing nothing.
- **A very big change** opens cut at 6,000 lines (`DIFF_LINES`) and says so; `Show all` lifts it to 200,000 and 32 MB. The 20 MB case is cut where git runs, not here.
- **Narrow panes** (under 900 pt, `layoutFor`) fold the list into the bar above the diff (`Files`), see above.
- **A new file** (`added`, `untracked`) is drawn as plain code: one number column, no tint, no bar, no `+` column, no hunk line (`DiffLayout::Code`). Every row would say "added", which the header says once with `new file`. An ordinary diff keeps the `+`/`−` column, the 2 pt bar and the row tint: the tint stays because the sign is one character away from the end of a long line and the changed words (`code-add-word`) need the row as their ground; how heavy it is is the `code-add-bg` token (`lib/theme/code.ts`), not the renderer. Unverified: whether a fainter token is enough.
- **Calm**: no signal colour (a change is `+`/`−` in its own column, never only a tint), nothing moves at rest, and nothing is drawn for a tab that is not in front.

## Where it opens from

`Review changes` (`mod+shift+g`, the Go menu, the palette), the `Changes` chip in a chat's header (the count of changed files from `lib/changes-count.ts`: one read when the chat comes to the front and one when its agent changes state, no timer), `Changes` in a project's sidebar menu (one entry per checkout when there are several) and on its card.

## Reading git

All of it is `herdr_core::git` (`native/core/src/git`), reached through the `Git` module (`native/app/src/git.rs`). The rules are in its module doc and each has a test in `native/core/tests/git.rs`:

1. **A read takes no lock the agent could collide with.** `status` runs with `GIT_OPTIONAL_LOCKS=0`; tracked patches use `diff-index`, because the porcelain `diff` rewrites the index (and takes `index.lock`) when a timestamp moved.
2. **A repository's own config runs nothing**: no fsmonitor, textconv or external diff; paths are literal (`GIT_LITERAL_PATHSPECS`), so a file called `*` is a file.
3. **Output is bounded where git runs** (locally by killing our own child by PID, remotely inside `git.py`).
4. **A remote machine** runs `git.py` over the machine's shared ssh connection: every path is one argument, validated by `validate_dir` and `validate_rel` first.

The tab reads when it comes to the front, every `POLL_MS` (5 s, stretched to four times a slow read) while it is in front and the window is on screen (focused or not; `background` reads nothing), and `TURN_MS` after an agent of the checkout changes state. A hidden tab, or a window in the background, reads nothing.

## Reviewing

- `j` and `k` move between files (Up and Down too while the list has the keyboard), `n` and `p` between the changes of a file, `Enter` shows more unchanged lines while the list has the keyboard (3, 12, the whole file: `CONTEXTS`; the file's menu has them as `Context` radios, with no key hint because the key depends on where the focus is), `x` marks the file reviewed, `r` reads again, `c` writes a note on the change in view.
- **Reviewed** marks are saved per checkout (`changes.reviewed.v1` in the settings file) against the file's `fingerprint`, a hash of its working-tree content: an edit since, even one that keeps the line counts, takes the mark back.
- **A note** is on a group of changed lines (the unit `n` and `p` step through), one per group. A note on one line would need `CodeDiff` to report which row has the focus; it only reports the change it stepped to (`CodeDiffEvent::Change`), and teaching its renderer a line focus is a change to `native/app/src/highlight/view` that was not made. It is kept with its `path:line`, the changed lines it is about and the person's words. Notes live in memory for as long as the app runs, per tab, so a project switch keeps them.

## Sending notes to the agent

`mod+Enter` opens a preview (`SendNotes`) with the whole message, exactly as the agent will get it (`notesMessage`: a line saying what it is, then per note `path:line`, the quoted lines, the words), and the agent to send it to: a radio group when several work in the checkout, nothing chosen until the person chooses. `Send` is the only thing that sends. A chat goes through `Sessions.send`, a terminal agent through `Herdr.sendInput`; a terminal agent that is waiting on a question is listed and cannot be chosen, because text typed there would answer it. With no agent in the folder the message can be copied. An agent is "in the checkout" by canonical paths (`agentsIn`, `Git.canonicalPath`): git names the checkout by its real path and an agent's folder may be a link to it (`/var` for `/private/var` on macOS). Another machine's paths are compared as that machine wrote them, since only it can resolve them. A note on a file that changed after it was written says so.

## Taking a change back

`Revert this change…` (after the actions on a change) and `Revert this file…` (last), each after a divider so the two are never adjacent (the file's menu, `changeEntries`) go through `confirmDestructive` that names what is lost, then `Git.revertFile` or `Git.revertGroup`, then a toast with `Undo`. Before anything is removed its patch is saved for ten minutes (`UndoStore`); a change too big to save (`BACKUP_CAP`) is refused. A change is reverted only if the diff is still the one the person saw (`fingerprint`) and `git apply -R --check` accepts the reverse patch. A file with merge conflicts, a new or deleted file (as a piece) and another repository are refused with the reason. The revert is on the working tree and the index of that file; the app never stages or commits.

## Accessibility

The list is `Changed files`; each file's change is a group named `Change to <path>`; the diff is named by `diffLabel`. Selecting a file, adding or removing a note, marking reviewed, a revert and a refresh each announce. A field that closes gives the keyboard back to `Add note`. Every control has a name and a key hint.

## Folders reached by a link

A tab's folder, a project's checkouts and an agent's folder are compared after `Git.canonicalPath` (`agentsIn`, `projectOfFolder`, `checkoutNameOf`), because git names a checkout by its real path and another source may hold a link to it (`/var/x` for `/private/var/x`). Limit: a remote machine's paths stay as given, so a link there is not followed.
